# Go 生成任务使用 RabbitMQ 分发、Redis 通知和 PostgreSQL 权威状态

迁移到 Go 的生成领域使用 RabbitMQ 分发待处理任务，Redis Pub/Sub 向多个 Go API 实例广播进度变化，PostgreSQL 保存任务、输入快照、租约、供应商任务 ID、当前状态和不可变任务事件。消息只携带任务 ID、事件 ID 等定位信息，不保存生成输入、供应商密钥或权威进度。此决定适用于迁移后的 Go 生成领域；Next.js 现有 SQLite Worker 与通知机制在切换前继续运行，前端代码暂不改动。

Go API 在事务中写入任务与 outbox 记录，返回任务 ID；独立的 Go Worker 进程消费 RabbitMQ 消息，按 PostgreSQL 中的状态、租约和供应商连接名额领取任务。Outbox 发布器使用 RabbitMQ 发布确认，消费端使用手动确认；重复消息、消息丢失后的补发和进程重启均以数据库记录为依据恢复。Worker 不把一次长时间运行的供应商任务绑定在一条未确认的 RabbitMQ 消息上。Redis 通知在数据库事件提交之后发布，订阅者断线后从数据库补查最新状态；Redis 不承担任务持久化或进度回放。

RunningHub 的 WebSocket 用于获取实际进度，HTTP 查询原供应商任务 ID 用于断线和重启后的恢复。只有经实际工作流验证的百分比才作为百分比提供，否则只提供真实阶段。供应商付费提交的响应不明确时，标记为待核实并阻止自动重提。熔断暂停新的供应商提交，不阻止对已提交任务的查询和结果保存。供应商并发名额由数据库中的领取／租约规则控制，不能仅依赖 RabbitMQ prefetch 或 Go 进程内计数。

排队首版只提供普通与加急两档。管理员可以加急或取消加急尚未开始供应商提交的任务，操作写入审计；普通用户和创作助手不能设置优先级。加急任务只在同一平台连接的新提交任务中优先，多个加急任务仍按原排队顺序领取，不能越过已提交任务的查询和已有结果的保存，也不能绕过提交熔断。不提供任意权重、拖拽排序、等待老化或复杂公平调度。

提交熔断按平台连接判断。连接失败、请求超时、HTTP 429 或供应商 5xx 连续发生五次后暂停新提交；参数错误、内容审核拒绝、用户取消、节点删除和普通生成失败不计入。冷却依次为一分钟、五分钟和十五分钟，后续保持十五分钟；429 带有 `Retry-After` 时取该值与当前冷却时间中的较长者。冷却结束后不创建额外探测请求，而以该连接下一项已经确认的排队任务试探；供应商明确接受提交即关闭熔断并重置冷却阶梯，试探失败则进入下一档。后台只展示熔断状态、原因和下次试探时间，不提供人工强制打开或关闭熔断。

此方案增加 RabbitMQ、Redis 和 outbox 的运维与一致性成本，换取任务分发与跨实例通知的独立扩展能力。ADR-0002 和 ADR-0003 的 SQLite 队列与 Web 通知选择仍描述未迁移应用；迁移切换后的队列与通知选择由本 ADR 取代。账户和生成领域仍按 ADR-0018 分别迁移，不引入平台积分或用户扣费。
