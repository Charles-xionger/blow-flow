# AI Flow 平台优化设计方案

> 修订日期：2026-10-30。
> 目标：先解决当前平移、缩放、拖动卡顿，再为 Agent 编排和大规模画布建立扩展边界。

## 1. 当前问题与设计依据

| 代码位置                                      | 已确认的行为                                              | 潜在影响                               |
| --------------------------------------------- | --------------------------------------------------------- | -------------------------------------- |
| `components/canvas/Canvas.tsx`                | 每次视口变化写入 Store，画布订阅整个 Store                | 平移缩放带动无关组件更新               |
| `store/useCanvasStore.ts`                     | persist 保存全部节点、连线、视口，每次 set 进入持久化链路 | 高频全量序列化及同步 localStorage 写入 |
| `components/canvas/Sidebar.tsx`、`TopBar.tsx` | 订阅整个 Store                                            | 无关位置变化触发渲染                   |
| `components/nodes/` 多种节点                  | 订阅完整 nodes，部分遍历上游节点和连线                    | 一个节点移动带动多个节点重算           |
| `store/useCanvasStore.ts`                     | 每次节点变化重建选中数组，批量新增逐个 set                | 多余通知与重复持久化                   |
| 画布与节点样式                                | 默认连线动画、背景模糊和媒体预览                          | 绘制成本需实测确认                     |

以上是静态代码证据，尚未测量各项实际耗时。十万节点、多人协作和分块加载不能被预设为当前必需能力。

## 2. 架构原则

1. **分离业务文档、交互会话和运行状态。** 节点内容与连线属于业务文档；视口、悬停、选择属于交互会话；任务进度和流式输出按任务或节点定向更新。
2. **高频位置更新保持实时，持久化合并。** 允许受影响的外壳与连线更新，避免无关业务内容重渲染，不追求“任何 React 子树零渲染”。
3. **保持几何一致性。** 不绕过 React Flow 的位置系统直接修改节点 DOM transform；拖动中的节点、Handle、连线、框选、父子关系必须同步。
4. **明确状态所有权。** 近期保留 Zustand 与受控 React Flow；未来引入业务内核后，由内核持有业务状态，渲染适配层管理临时交互，避免双向全量同步循环。
5. **计算内核不依赖 DOM。** 命令校验、拓扑和布局可独立测试；真实尺寸由浏览器测量适配层提供。
6. **Agent 表达语义和关系。** 布局器计算坐标，尊重人工固定的位置。此项是本项目设计选择，不是对 ComfyArt 已有实现的描述。
7. **按证据引入依赖。** 空间索引、Worker、CRDT 和分块存储不是基础优化的前置依赖。

## 3. 分阶段路线

| 阶段 | 工作                               | 进入条件                         |
| ---- | ---------------------------------- | -------------------------------- |
| P0   | 性能基线、订阅与持久化治理         | 立即实施                         |
| P1   | 外壳与内容隔离、媒体和可见性优化   | 根据 P0 后的剩余瓶颈选择         |
| P2   | 业务命令内核、批量事务、Agent 布局 | 有明确批量编排需求               |
| P3   | 空间索引、自定义视口投影、分块加载 | 实测证明当前方案不能满足目标规模 |
| P4   | 多端协作和增量同步                 | 明确并发编辑与离线同步需求       |

每阶段独立交付，不将状态库、渲染器和存储格式一次性替换。

## 4. P0：当前卡顿治理

### 4.1 性能基线

使用生产构建，记录硬件、浏览器、屏幕、DPR、提交版本和媒体预热状态。初始测试覆盖 20、100个点，后续按实际规模扩展。

样本包含文本、图片、视频、分组、不同连线密度和选中面板。分别执行平移、缩放、单节点拖动、多选拖动、分组拖动、输入和批量新增。

记录帧耗时分布、长任务、React 提交次数及耗时、序列化与存储次数、DOM 数量、内存和媒体资源占用。同场景重复至少 3 次，保留可对照数据。

### 4.2 持久化调度

移除高频画布 Store 的全量自动 persist 链路。仅缩减 partialize 字段或延迟 storage.setItem 不一定消除序列化；应在生成快照与 JSON.stringify 之前合并更新。

| 数据                     | 策略                                             |
| ------------------------ | ------------------------------------------------ |
| 主题等小型偏好           | 独立保存，使用带版本的 localStorage              |
| 实时视口、拖动位置、悬停 | 内存更新，不触发全量保存                         |
| 节点、连线和最终位置     | 标记 dirty，由保存调度器生成快照                 |
| 本地恢复副本             | 异步 IndexedDB，成功写入后记录已保存版本         |
| 服务端工作流             | 保留现有 API 与 SQLite，成功响应后记录服务端版本 |
| 图片和视频               | 保存媒体引用，避免在快照内重复嵌入大体积内容     |

具体约束：

- 受控 React Flow 继续实时接收位置；拖动结束再请求持久化。多选和分组作为一次业务操作处理。
- 受控 viewport 保持实时更新，但与文档保存解耦；移动结束保存最终视口。若改为非受控，先设计加载和恢复桥接。
- 文本保存可从 500ms 防抖、2s 最大等待开始调优。该参数为初始建议，不是已验证最优值。
- 手动保存立即读取最新业务状态，绕过防抖；明确区分本地已保存与服务端已保存。
- 保存队列串行执行，携带 workflowId 与单调递增版本，避免旧响应清除新修改的 dirty 标记。
- 切换项目前处理待保存队列，旧任务不得写入新项目。卸载/隐藏时尽力刷新，但不依赖退出事件保证异步写入成功。
- 配额、权限、网络或写入错误时保留 dirty 状态，并提供恢复提示；明确异常退出的未保存窗口，不承诺零丢失。
- 迁移旧 canvas-storage 时验证格式，新副本成功写入并验证前保留旧副本；加入 schemaVersion 与幂等迁移标记。

### 4.3 订阅与批量更新

- 侧栏、顶栏、菜单只选择实际需要的字段和 action，避免无参数 useCanvasStore()。
- 仅在保存、点击事件中使用的数据，在回调执行时读取，不为事件处理订阅全部节点。
- 节点只订阅自身数据及实际依赖的上游结果；选择器保持稳定引用，避免无条件构造新数组/对象。
- 将业务内容和节点位置分离，位置更新尽量只影响外壳。取得自身位置不应要求订阅全部 nodes。
- 选中集合未变化时保持原引用，不能因位置变化重建 selectedNodeIds。
- 批量新增节点与连线一次计算、一次 set。
- 稳定 defaultEdgeOptions、回调等 React Flow 属性引用。
- 上游查找仍有明显成本时，再引入按 ID 的实体表和入边索引，不为少量查找提前全面重构。

### 4.4 验收

- 连续平移/缩放不触发整份工作流序列化和 localStorage 写入。
- 拖动时，无依赖关系的业务内容、侧栏和顶栏不因坐标变化持续提交；必要外壳与连线更新除外。
- 批量新增在业务 Store 层一次提交，结果与原行为一致。
- 保存刷新、URL 加载、项目切换、主题恢复及旧缓存迁移通过验证。
- 报告相同基线的帧耗时与长任务变化，不在测量前承诺提升比例。

## 5. P1：渲染与媒体优化

### 5.1 统一外壳

基于现有 BaseNodeWrapper、BaseNode 和业务节点渐进整理，避免长期并存多套包装体系。

```text
NodeShell：选中高亮、Handle、尺寸、交互边界、细节级别
└── NodeBody：提示词、参数、媒体预览、生成结果
```

React Flow 继续负责位置与连线几何。NodeBody 尽量不接收每帧变化的坐标。Handle ID 与方向保持兼容，不能直接替换为统一四边端口。

复用已有测量能力或 ResizeObserver，比较尺寸变化并合并通知，避免测量反馈循环。验证中文输入、焦点、弹窗、节点内滚动和快捷键。

### 5.2 流式内容、LOD 与媒体

- Token 按节点 ID 定向通知并缓冲，按帧或可配置周期更新当前内容，不写全局图状态。
- 不用 innerText 覆盖 React 管理的 Markdown 或表单。命令式文本如确有收益，应使用 React 不管理子内容的隔离容器，明确清理与最终提交协议。
- 可试验 zoom < 0.3 简化、zoom > 0.35 恢复的滞回阈值，避免边界反复挂载；阈值需实测。
- 简化时保持稳定尺寸、Handle、草稿、任务订阅和编辑状态。节点简化不会自动降低 SVG 连线成本，边的动画和密度需单独处理。
- 图片按显示尺寸、缩放和 DPR 选择预览资源；视频使用 poster、延迟加载，按可见性与用户意图播放。
- 拖动时可隐藏非必要浮动工具栏，但不能丢失输入和焦点状态。
- 卸载和切换项目时释放不再使用的媒体资源，避免重复订阅生成任务。

### 5.3 内置可见性渲染优先

分别压测 onlyRenderVisibleElements 开关。它减少离屏绘制，但增加可见性计算与挂载切换成本，并非必然更快。

本阶段仍向 React Flow 提供完整图，验证离屏返回后的草稿、媒体状态、尺寸、分组和连线。验收以帧耗时、可见业务节点数和每节点 DOM 成本为准，不承诺整个页面 DOM 少于 200。

## 6. P2：业务内核与 Agent

### 6.1 边界与事务

沿用根目录布局，可渐进增加 lib/canvas-core、lib/canvas-layout 及浏览器适配层，不为此迁移项目到 src。

内核负责实体、拓扑、校验、批量变更、版本与可撤销命令；UI 提供测量与渲染；存储负责快照、日志和恢复。

runTransaction 先校验并计算候选结果，再原子提交，失败不留下半完成节点或悬空连线。一次业务事务不代表跨客户端或跨服务事务。

布局带 expectedRevision；提交前发现人工移动、节点删除或分组改变时拒绝过期结果或重新计算。人工固定节点不得被自动布局覆盖。

### 6.2 Agent 契约

复用现有 NodeType，按类型定义输入白名单和运行时 Schema。示意如下，实施时须补齐实际字段校验：

```ts
type NodeRef = { id: string } | { localId: string };
type CanvasOperation =
  | {
      action: "CREATE";
      localId: string;
      nodeType: NodeType;
      input: Record<string, unknown>; // 实施时替换为各类型的可写字段 Schema
      placement?: {
        anchor: NodeRef;
        direction: "RIGHT" | "BOTTOM" | "AUTO";
      };
    }
  | {
      action: "CONNECT";
      source: NodeRef;
      target: NodeRef;
      sourceHandle: string;
      targetHandle: string | null;
    };
interface CanvasCommandBatch {
  workflowId: string;
  requestId: string;
  expectedRevision: number;
  operations: CanvasOperation[];
}
```

批量新增以 operations 表达，追加子节点由创建、锚点布局和连接组合表达。返回新 revision、localId 映射和明确错误。

校验工作流访问权限、节点类型、字段、引用、端口兼容、批量大小和重复请求。相同 requestId 重试不能重复插入，Agent 不直接写入凭据、任务状态和生成结果。

### 6.3 布局与上下文

- 初期使用默认尺寸与实测缓存，内容变化后局部修正；未知尺寸不能承诺首次布局绝对无重叠。
- 小批量可使用本地轻量算法，计算成为瓶颈后再引入 Worker/ELK。
- 明确 parentId 下的局部与全局坐标转换，保持分组约束。
- 上下文结合拓扑和空间邻近，并限制文本预算；执行、导出和上游输入读取完整业务图，不读取可见节点子集。

验收覆盖 20 个关联节点一次批量创建和布局、幂等、过期 revision、失败回滚、布局期间人工操作、锚点删除、尺寸变化和分组内创建。

## 7. P3：大规模画布（按需）

### 7.1 空间索引

测量证明空间查询成为瓶颈后再引入 R-tree。索引存 ID 和包围盒，大文本与媒体独立。维护父子转换后的全局边界，变更时增量更新受影响祖先、后代和连接关系。

范围查询成本必须考虑命中数 K；不能把总成本只写为 O(log N)。分别测试初始化、查询、批量更新和 Worker 通信，说明 N、K、更新数、分布、硬件及 P95。5 万/10 万节点只是压力样本，不承诺所有查询和批量更新均在 3ms 内。

### 7.2 自定义视口投影

仅在内置策略不能满足已定义目标时制作独立原型，必须解决：

1. 保留边所需的两端位置、尺寸和 Handle 信息，或设计独立边渲染适配，不能依赖缺失端点的默认连线。
2. 两端均离屏但路径穿过视口的连线。
3. 分组祖先、选中、编辑中、拖动中节点及自动平移上下文。
4. 全选、框选、全图适配、定位、执行和导出使用完整业务图。
5. 不硬截断为 50～100 个可见节点；密集视图定义聚合或 LOD 规则。
6. 视口缓冲可从 20%～30% 起步调优，集合未变化时复用引用，避免每帧重建投影。

### 7.3 分块与内存

空间分块不等同业务分片：

- ChunkKey = floor(x / chunkSize) + "\_" + floor(y / chunkSize) 只定义锚点归属；大节点跨块检索需覆盖相交区域。
- 根据视口覆盖、缩放、缓冲和内存预算加载，不能固定九宫格。
- 明确跨块移动、跨块边、删除和索引一致性以及失败恢复。
- 未保存、拖动、编辑或任务引用的数据不能直接 LRU 淘汰，释放正文时保留必要几何和拓扑摘要。
- 配套后端按需读取接口；前端拆快照不能解决后端仍需全量下载的问题。

验收记录冷启动字节数、首屏交互时间、连续漫游后的内存平台值，并覆盖密集、跨块和超大节点场景。

## 8. P4：协作同步（按需）

选择 Loro/Yjs 前明确并发需求，验证协议而非仅安装依赖：

- 同节点并发移动、删除与编辑、Agent 与人工操作的冲突结果。
- 文本字符级合并和其他字段的冲突策略。
- 文档分片边界；完整 CRDT 文档仍驻留时，淘汰 Chunk 缓存不代表释放所有数据。
- 跨片原子性、协调方式、失败恢复。
- 请求去重、服务器确认、断线重放、快照压缩、日志保留、版本迁移和权限。
- 区分已显示、本地落盘、服务器确认三种状态。

使用所选库固定版本的官方 API。故障测试覆盖断网、崩溃、配额和重复消息，不宣称未经验证的零丢失、无锁或无冲突。

## 9. ComfyArt 的可迁移经验

详细证据见 [ComfyArt画布实现调研](ComfyArt画布实现调研.md)。研究仅为源码分析，未验证帧率或容量。

- ComfyArt 使用 tldraw，文档变更触发 800ms 防抖保存，相机属于 session 状态；保存仍是全量快照，不是增量 CRDT。
- tldraw 内核实时更新位置，并通过细粒度响应更新外壳；不能推导为业务层直接改 DOM、松手才同步引擎。
- 图片分级预览、视频按需播放、拖动隐藏浮动工具栏可优先借鉴。
- 自定义形状几何与业务组件分层、任务进度独立管理、批量编辑与父子坐标转换值得参考。
- ComfyArt Agent 允许像素坐标，应用没有证明十万节点或多端 CRDT 协作能力。
- 不为了模仿 ComfyArt 立即替换 React Flow；创作白板与带 Handle 的生成工作流具有不同交互需求。

多模型接入另见 [ComfyArt多模型接入分层调研](ComfyArt多模型接入分层调研.md)，不作为画布性能 P0 的前置重构。

## 10. 迁移、验证与参考

保留旧工作流 API 和 SQLite 数据可读，格式变化需兼容与回退。优先为保存队列、迁移、事务、版本冲突编写正确性测试；可逆订阅和样式调整使用针对性交互验证。

回归覆盖保存/刷新、URL 项目切换、复制删除、多选、分组、连线输入、快捷键、中文输入、角色引用、图片/视频结果和任务恢复。

在固定设备和生产构建上设定帧预算、P95 和长任务阈值，记录基线后确认目标。性能报告区分 CPU、React、绘制、网络和存储；不以模型生成速度代替画布交互性能，也不作无条件 60 FPS 承诺。
