# 节点持续拖动性能设计讨论

本文件记录 grill-with-docs 三轮讨论中已确认的边界及据此形成的实施设计，待最终确认共同理解后实施。与现有 spec.md 中解决拖动开始时控制台挂载的工作区分；当前没有宣称性能问题已修复。

## 已确认的边界

- 本轮处理节点从按下、持续拖动到松手的完整过程，包括移动原图节点引发下游视频节点更新的场景。画布平移和缩放做回归检查，独立瓶颈另行评估是否扩展范围。
- 在用户当前电脑上，以生产构建作为主要验收环境；同一份项目、相同拖动动作进行前后对照。优先消除交互期间超过 50ms 的长任务，并以接近 60fps 为目标。开发构建单独测量和报告。
- 节点展示区可以使用适配显示尺寸的画布预览图；查看完整图片时允许短暂先显示预览，再加载原图。生成和下载继续使用原始素材。
- 已有项目的上传原图、生成图片和角色参考图片均自动覆盖，不要求重新上传；按需生成并缓存预览，不一次性处理全部历史素材。
- 画布缩放时继续使用有尺寸上限的预览图，只有打开完整图片查看器才加载原图。接受高倍画布缩放时预览清晰度受限。
- 预览生成或加载失败时保留已有可用预览；没有可用预览时显示可重试占位，提供主动查看原图入口，不自动回退加载原图。
- 由现有应用服务端按需生成预览，作为可清除、可重建的缓存，不写入项目内容或生成任务快照。同一原素材与预览规格复用缓存，原素材身份或规格变化后使用新缓存；接受首次等待与服务端处理、存储开销。
- 初始预览规格为长边最多 1024 像素，小图不放大，保留透明背景；GIF 等动图在画布上使用静态首帧，完整查看器使用原图。规格调整必须依据清晰度和性能实测。
- 验收对比原始基线、只改预览、只改订阅、两者一起四种配置，分别覆盖首次加载与缓存命中。生产构建使用有界面的浏览器、真实高像素 PNG 和原图连接视频节点场景；不能复现原问题时明确报告验证缺口。

## 诊断证据与限制

- 用户提供的压缩 Chrome Performance 录制约 8.7 秒，包含约 6 秒原图节点拖动。
- 同一 LazyPixelRef=948 的 PNG 解码四次，约 199、305、356、294ms；同期浏览器图层提交约 174、305、364、270ms，在解码和上传完成后结束。重复解码的具体触发条件尚未确定，图片标识尚未映射到文件名。
- TaskVideoNode 订阅完整上游节点对象。用当前真实 selector 和 applyNodeChanges 验证：仅改变位置且保持 data 引用不变，也会使 sources 浅比较发生变化，触发下游更新。
- 拖动期间 147 次 mousemove 处理的中位数约 25.5ms，P95 约 44.1ms。录制为开发构建，含 React 调试开销，不能直接视为生产耗时。
- 录制内的 Canvas、BaseNode、NodeShell、TaskVideoNode 源码与分析时工作区文件一致，已包含现有拖动开始时避免挂载控制台的改动。

## 已查明的实现约束

- 当前没有画布预览图生成链路；imageSrc 同时用于节点展示、完整预览、下载、角色素材和下游生成输入，不能直接用预览地址覆写它。
- H3 的参考素材 URL 校验拒绝 query/hash；若使用 OSS 图片变换参数，必须与提交给生成接口的原素材 URL 分离。Bucket 是否支持所需变换尚未验证。
- 现有浏览器测试服务使用 next dev；拖动长任务断言是两个节点的轻量场景。H3 图片夹具为 64×64，上传测试的大文件通过追加字节构造，均不能代表高像素 PNG 解码成本。
- 旧 spec 中生产测量的场景不含 H3，且未找到对应可运行夹具。其不优化 selector 的结论仅针对旧场景，本次下游视频节点的证据需要单独验证。
- 既有 ADR 没有明确禁止最终图片的轻量展示；预览设计仍须遵守生成任务输入与结果快照、原始产物保存和失败恢复约束。
- 已核对安装的 Next 16.1.6 源码：内置优化对动画 GIF/APNG/WebP 原样返回，转换异常时也可返回原图，公开接口只有宽度限制，不能直接满足静态首帧、最长边上限和禁止原图回退。Sharp 已由 Next 间接安装且原生转换验证可用，自建接口应声明直接依赖。

## 实施设计

### 预览链路

- 在当前应用中提供独立预览接口，用 Sharp 处理首帧、方向和尺寸，输出保留透明通道的静态图片；宽高共同约束在 1024 像素内。不能直接包装 /_next/image 并假定其不会返回原图。
- 缓存以原素材身份或版本与预览规格版本为依据。预览为派生数据，独立于项目保存、生成任务和原始 OSS 产物；清理或丢失后允许重建，不迁移旧项目快照。
- 同一缓存键的并发请求合并，不同源图转换限制并发；设置下载、解码和缓存容量边界，避免冷缓存把压力转移到服务端。具体资源参数在实现时根据真实素材和部署容量选择并记录。
- 缓存支持有界清理，失败结果不永久缓存。源内容被替换时必须使对应预览失效；不能仅假定所有外部 URL 永远不变。
- 图片读取遵循应用原素材访问范围，对外部地址、重定向和本地地址做明确校验；接口不成为任意地址下载代理。历史来源兼容性在接入前盘点，无法处理的来源遵循已确认的错误展示策略。
- 旧项目的上传图片、生成图片及角色参考图片在展示时按需获得预览。画布内实际可见的参考图片缩略展示也使用同一预览链路，避免控制台中的原图绕过限制；原素材仍用于生成、下载和完整查看。
- 预览未就绪时保持节点展示区几何稳定。已有预览仅指当前素材的可用预览；换图后不得把上一素材继续呈现为当前结果。错误提供重试与主动查看原图入口，不悄悄回退原图。

### 移动与内容更新分离

- TaskVideoNode 的上游订阅只依赖参考素材内容和身份，而非包含 position、dragging 等属性的完整节点对象。
- 上游位置变化不触发下游素材区重算；连线、连线顺序、素材 URL、名称与引用所需字段变化仍及时更新，生成结果到达不能因性能优化被延迟或漏掉。
- 将昂贵内容与仅负责位置变化的节点外壳隔离，避免父级每次移动都重新创建整棵控制台 JSX。已有控制台挂载与隐藏语义保持，不能通过清空节点内容掩盖性能问题。
- 先测量以上改变的独立收益，再决定是否扩大 CanvasInner 或 MiniMap 等组件优化范围。

### 验收与实验顺序

1. 固定真实项目的可重放副本、浏览器窗口、缩放、设备像素比和拖动路径，记录原素材像素尺寸及格式。测试不发起真实生成、不改用户项目；用隔离数据与结果事件验证素材更新。
2. 在有界面生产构建中建立基线，覆盖原图连接 H3 视频节点，以及未选中和已选中节点的按下、持续拖动、松手阶段。采样脚本和场景保留为可重跑的性能夹具。
3. 运行四种配置乘以冷、热缓存两种状态的对照；每种至少三次。冷态区分首次服务端生成、首次浏览器加载，热态使用已生成且已加载的预览，避免混淆缓存层。
4. 记录浏览器帧呈现、超过 50ms 的主线程任务、图片解码、图层提交等待、下游重渲染及首次预览等待。鼠标事件耗时或 requestAnimationFrame 频率只能作为辅助，不能替代真实帧呈现结论。
5. 预览链路验证横图、竖图、细长图、小图、透明图、动图首帧、损坏图和不可读取来源；检查长边上限、失败不回原图、并发去重及清理后重建。订阅回归覆盖位置变化不更新，以及真实素材变化仍更新。
6. 功能回归包括原始生成参考、下载、完整查看、旧项目、角色素材、控制台输入保留，以及画布平移缩放；确认原图 URL 未被预览 URL 污染。
7. 生产场景仍出现超过 50ms 的交互长任务时继续按 trace 归因，不能以开发模式较慢解释生产失败。若原问题在受控基线中未复现，记录已验证的机制修正与仍缺失的真实环境证据，不宣布卡顿已解决。
