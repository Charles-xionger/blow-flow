# 06: 加急任务与阶梯式提交熔断

**What to build:** 在现有 Go 生成任务链路上增加管理员可审计的普通／加急排队，并把既有通用操作熔断收窄为按平台连接生效的提交熔断。只实现已确认的领取顺序、故障分类、冷却阶梯和管理接口，不增加拖拽排序、任意权重、人工强制开关或额外探测任务。

**Blocked by:** None（01—05 已在 `codex/go-generation-integration` 实现并随 Go cutover 合入 `main`）。

**Status:** ready-for-agent

## Context

遵循 ADR-0021、`docs/architecture/go-generation-migration.md` 和根目录 `GLOSSARY.md`。数据库是任务优先级、领取顺序、熔断状态与审计记录的权威来源。RabbitMQ 只唤醒 Worker；加急和冷却结束后的试探都必须通过相同的数据库领取路径。

## Acceptance criteria

- [ ] 生成任务只有普通和加急两档。已认证管理员可通过 Go 管理 API 加急或取消加急尚未开始供应商提交的排队任务；普通用户、创作助手和运行中任务不能调整。成功操作写入审计，重复设置保持幂等。
- [ ] 同一平台连接有空闲提交名额时，先按原创建顺序领取加急任务，再按原创建顺序领取普通任务；加急不改变输入、连接并发和排队上限，不绕过提交熔断，也不抢占到期查询或结果保存。
- [ ] 提交熔断只按平台连接生效。连接失败、请求超时、HTTP 429 和供应商 5xx 连续五次打开熔断；参数错误、内容审核拒绝、用户取消、节点删除、普通生成失败及成功提交会按规则中断或重置连续计数。
- [ ] 熔断冷却阶梯为 1 分钟、5 分钟、15 分钟，后续保持 15 分钟；429 的 `Retry-After` 使用它与当前阶梯中的较长者。冷却结束后只允许该连接下一项已确认排队任务试探，不创建额外探测请求。
- [ ] 供应商明确接受试探提交后关闭熔断、重置冷却阶梯和连续失败计数；试探再次出现计入范围的故障时进入下一档。已提交任务的查询和已有结果的保存始终继续。
- [ ] 管理接口展示任务是否加急，以及平台连接熔断的正常／暂停提交／试探恢复状态、最近原因和下次试探时间；不提供人工强制打开或关闭。OpenAPI 契约、迁移和测试覆盖权限、排序、故障分类、阶梯冷却、`Retry-After` 与真实排队任务试探。
